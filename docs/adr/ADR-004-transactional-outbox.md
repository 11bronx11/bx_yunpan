# ADR-004：使用 Transactional Outbox

- 状态：Accepted
- 日期：2026-08-14
- 决策者：项目维护者

## 背景

上传完成、文件创建、删除、分享导入等业务事务会触发对象校验、缩略图、AI 索引、GC 和审计等异步副作用。如果业务表提交后直接发布 Redis/Asynq，进程可能在两步之间退出，产生“数据库成功但任务永久丢失”；如果先发布任务，则可能处理尚未提交的数据。

项目不引入 XA、TCC 或 Kafka 事务，但必须证明进程重启和重复投递不会破坏数据。

## 决策

业务事务在修改领域数据时，同一个 PostgreSQL 事务写入 `outbox_events`。`worker-system` 中的 Dispatcher 使用 `FOR UPDATE SKIP LOCKED` 批量领取可用事件，发布对应 Asynq 任务，再记录发布时间。

交付语义为至少一次，不承诺恰好一次。每个事件包含稳定 EventID、类型、版本、AggregateID、发生时间和 Trace Context。消费者通过 `(event_id, consumer_name)` 消费记录及业务唯一约束实现幂等。

Dispatcher 自身是 PostgreSQL 轮询器，不是 Asynq 任务，避免“需要先投递任务才能启动投递器”的闭环。

## 后果

正面影响：

- 业务事实与“需要发生的副作用”原子提交。
- Redis、Worker 或进程短暂故障不会永久丢任务。
- 支持重放、延迟、失败观测和迁移到其他消息系统。
- 领域事件形成未来拆分服务的稳定边界。

代价：

- 系统是最终一致，不是请求返回时所有副作用都完成。
- 需要 Dispatcher、重试、积压指标和事件清理策略。
- 至少一次投递要求每个消费者真正幂等。

## 被否决方案

### 事务提交后直接 Enqueue

否决原因：提交与发布之间存在不可恢复的丢失窗口。

### 分布式事务

否决原因：PostgreSQL、Redis 和 MinIO 之间引入 XA/TCC 成本过高，且对象存储不提供同等事务语义。

### 只使用定时全表扫描

否决原因：可以作为补偿，但无法清晰表达事件版本、因果关系和任务状态。

## 约束

- Outbox Payload 不包含 Secret、预签名 URL 或完整文件内容。
- 业务事务内只写 Outbox，不调用外部网络。
- Dispatcher 发布前后退出都必须可以安全恢复。
- Outbox 积压、最老事件延迟和失败次数必须有 Metrics。
