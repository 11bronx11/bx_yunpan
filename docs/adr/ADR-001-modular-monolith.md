# ADR-001：采用模块化单体 API

- 状态：Accepted
- 日期：2026-08-14
- 决策者：项目维护者

## 背景

目标系统包含身份、目录、对象、上传、分享、媒体、AI、搜索、任务和审计等边界。展示项目需要体现清晰架构与可演进性，但当前没有独立团队、海量流量或不同发布周期来证明拆分大量微服务的成本合理。

旧系统按 FastCGI 可执行文件拆接口，造成协议、认证、事务和错误处理分散。这种“多个进程”不是有效的领域边界，也不应原样翻译成多个 Go 服务。

## 决策

首个版本采用一个无状态 Go API 模块化单体，并使用一个可按角色启动的独立 Worker 二进制。

API 内按业务模块组织：

- Identity
- Drive
- Object
- Upload
- Sharing
- Search
- AI
- Task
- Outbox
- Audit

每个模块拥有自己的写模型。Transport 只调用 Application Use Case；模块之间通过窄接口或领域事件协作，不直接修改其他模块的数据表。

Media、AI 和 System Worker 使用同一个二进制，通过队列和角色配置独立部署。所有进程不依赖本地持久状态。

## 后果

正面影响：

- 单仓库、单 API 部署，事务边界和本地开发更简单。
- 仍能展示领域边界、依赖倒置、异步处理和独立扩容。
- OpenAPI、日志、认证和错误语义只有一个入口。
- 未来可以优先拆出 AI/Search，其次拆 Upload/Object。

代价：

- 模块隔离主要依赖代码评审、包依赖规则和测试，不是网络强隔离。
- API 的发布节奏仍然绑定。
- 热点模块不能单独扩容 API 计算，但 Worker 已可独立扩容。

## 被否决方案

### 从第一天拆微服务

否决原因：需要服务发现、远程调用、跨服务鉴权、分布式追踪、事件基础设施和部署编排，会显著延迟可演示主链路，且当前没有规模证据。

### 按旧 FastCGI 程序一对一建立 Go 服务

否决原因：延续按接口进程切分、事务分散和重复基础设施的问题，不形成稳定业务边界。

### 单包 CRUD 应用

否决原因：初期简单，但上传、对象、分享、AI 和 GC 会快速耦合，无法形成可解释的架构。

## 约束

- 禁止业务模块导入其他模块的数据库 Model。
- 禁止在 Handler 中编排复杂事务。
- 新跨模块行为必须先确定同步接口或领域事件所有者。
- 拆分服务必须有独立扩容、发布、故障隔离或团队所有权的真实理由。
