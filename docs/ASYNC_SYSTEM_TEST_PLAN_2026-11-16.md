## 1. 测试目标与结论边界

需要验证的实际链路：

```text
浏览器 → Web/Nginx → API → 业务 PG：事实 + outbox
                       ↓
async-control Relay → 控制 PG：inbox + 冻结计划 + task/source + 位点
                       ↓
有界调度 → RabbitMQ 工作队列 → upload/object/media/gc/AI/search
                       ↓
控制 PG：类型化结果 + computed/待发布 → 32 个 RabbitMQ 结果分片
                       ↓
committer → 业务 PG：前提复核 + 业务效果 + receipt + 后续事件
          → 控制 PG 回报 → ACK
```

文件字节由浏览器经同源 `/storage` 访问 MinIO。测试必须同时验证这条数据通路，不能仅证明 API 元数据操作成功。

验收回答六个问题：

1. 已受理的业务意图是否不丢失，重复、乱序、重启和故障后能否正确收敛？
2. 配额、引用、文件唯一性、对象世代、权限和终态是否始终正确？
3. 每种失败是否有限重试、可定位、可恢复，并且不会产生无限补偿链？
4. 控制面、MQ、计算和提交分别受压或失效时，是否保持资源有界及 API 的预期可用性？
5. 真正的独立进程、浏览器、代理、迁移和旧链路切换能否运行？
6. 跨主机故障和备份恢复后，正确性、恢复能力和可解释性是否成立？

本计划包含单元、性质/模糊测试、真实依赖集成、全链路冒烟、进程 E2E、浏览器 E2E、竞争、故障、回归、迁移、恢复、短时压力和观测验证。完整测试按第 14 节的执行包交付，单个绿色命令不能代替整份验收。

测试中发现缺陷，记录最小复现并修复后回归；不扩展为 AI 数据搬迁、业务读副本改造、冷热存储或在线动态分片工程。测试用只读对账器不接入线上恢复循环，不引入第二个任务权威。

同一 PG 实例的两个数据库不等于资源隔离。同宿主机的多容器不等于跨主机容灾。单节点 RabbitMQ 的进程重启不等于 quorum 集群成员故障；MinIO 单节点重启不等于存储集群容灾。

已有测试资源的名称/端口只见历史记录，本次未检查存活状态。执行前先只读盘点，不自动复用正在服务业务的 RabbitMQ 做 broker 重启、内存/磁盘告警或网络分区。vhost 只隔离命名和权限，不隔离 broker 故障及资源压力。

### 3.2 资源约束

- 每次运行生成 `run_id`，登记数据库/schema、MQ vhost/prefix、bucket/prefix、容器/网络、端口、角色实例和故障代理所有权。
- 业务/控制 DSN 必须指向专用测试资源，并核实数据库实际身份；不能只比较两个连接串字符串。只读角色必须拒绝业务写入和 DDL，不能以 `default_transaction_read_only` 代替数据库权限。
- 现有夹具隔离方式不同，部分用例会访问 `public`，部分使用 `LIKE public.*` 克隆。因此目标测试业务库先完整迁移，整套测试不能指向开发/现有业务库。
- 现有核心冒烟固定使用 `async-core-test` bucket，修改 lifecycle，schema 含 `public` 回退；测试入口必须核验这是测试 MinIO，而非只依赖前缀隔离。并行运行前补足 bucket/资源隔离，否则串行。
- MQ 传输故障用专用 broker；schema 隔离不能支持 PG 进程级故障，用独立测试 PG 实例。
- 部署 E2E 从 `deploy/.env` 约定派生配置，在隔离项目使用受保护测试配置；故障地址经测试代理/覆盖文件注入，不改用户 `.env`。避免多个入口手写两套不同配置。

- 构建串行进行；全量回归、浏览器、压力和 cold build 不同时争抢受限主机。`go test -p=1` 不代表跨包共享夹具天然安全。

## 4. 全部测试共用的判定器

### 4.1 必须持续成立的业务不变量

| 编号 | 判定 |
|---|---|
| INV-01 | 事实与 outbox 同事务；提交成功的测试事实有对应事件，回滚无事实/事件残留 |
| INV-02 | 每个已提交事件最终 accepted 或持久 quarantined；冻结计划内的来源/任务完整，未接管事件不能被位点越过 |
| INV-03 | 同语义工作只有稳定身份；重复来源不增加可用预算，终态自动恢复不重开 |
| INV-04 | 同一执行代次仅一个有效 token；旧持有者不能续租、改状态、覆盖当前结果 |
| INV-05 | computed 只补发同一结果；业务效果、receipt、必要后续事件同事务；重投不重复生效 |
| INV-06 | 每 owner `occupied_bytes = 活跃逻辑文件大小之和 + 所有未结算会话 reserved_bytes 之和`，非负且遵守准入额度 |
| INV-07 | 每对象 `reference_count = 未删除 file_entries 数量`；任何仍有活跃引用的对象可下载且内容一致 |
| INV-08 | 取消/失败/过期释放预留恰好一次；completed 会话有合法唯一逻辑文件且预留为零；晚到结果不逆转终态 |
| INV-09 | 删除字节必须有对应对象/位置/世代的删除授权；旧删除不能破坏新世代；单会话清理不能删除共享对象 |
| INV-10 | 文件/目录命名与内容身份唯一约束、跨 owner 权限持续成立；派生结果不决定授权 |
| INV-11 | 所有执行、派发、恢复、补发和补偿有限；耗尽/需人工处理有持久结论、日志和可检查资源 |
| INV-12 | 新增实例不放大全局额度；队列、内存、连接、事务、batch、confirm 窗口与在途执行均有上界 |
| INV-13 | 缓存/cursor 读取组合已提交的 API/async epoch；后台入库、删除、ACL 变化不会长期不可见或越权 |
| INV-14 | 维护不删唯一未提交结果、不删安全窗口内事件、不删停止屏障；重放不能重置预算或重复业务效果 |

“恰好一次”只指业务效果与结算，不要求消息只传一次。发生人为预算耗尽的用例可预期 `needs_attention`，但不能把它算作业务成功。

### 4.2 一致性采样与跨库对账

业务不变量在**同一个业务 SQL 快照**校验；不能先读配额再等事务提交后读文件，制造假差异。压力期间使用短只读事务持续采样；关键临界窗口由屏障控制观察。

跨库没有分布式快照。跨库对账必须先停止新生产，允许在途提交/回报排空，记录两库观察边界，再对每个 event/task/result/receipt 检查允许的中间态。仍在运行时只对单项链路和有时序证据的非法状态报警，不能把正常的“业务已提交、控制未回报”当数据损坏。

判定器按测试运行的真实 ID 集合查询，避免把其他测试的终态/积压算进来。SQL 是诊断与不变量验证，不能自动“修正”引用或配额。

### 4.3 结果状态和完整证据

每个场景记录 `PASS / FAIL / BLOCKED / NOT_RUN / EXCLUDED / KNOWN_DEFECT`。`EXCLUDED` 要有退役/不适用理由及替代场景；环境缺失是 BLOCKED；已知缺陷不能标 PASS。重试后通过保留首次失败、重试次数、原因和修复版本，禁止静默 rerun-until-green。

每个用例至少包含：场景 ID、优先级、层级、前置资源、随机 seed、输入、注入屏障、预期状态/预算/效果、恢复期限、实际结果、证据路径、清理/现场状态。

关键证据链应连通：

```text
run_id → request/idempotency key → session/operation/object
       → outbox(event_xid,seq,event_id) → inbox/plan/source
       → semantic_key/task/generation/token → result/digest
       → business receipt/领域行 → 控制回报 → MQ ACK → 定向清理
```

没有暴露 ACK 观测点时，结合 delivery tag、消费者日志和未确认消息变化取证；仅队列深度为零不算提交成功。

## 9. 严苛故障矩阵与注入方法

### 9.1 屏障优先于随机 sleep

先在 E1 用可控屏障证明正确性，再在 E2/E3 使用真实进程/网络故障复验。屏障位置：业务提交后、Relay 读取后/接管事务中、派发预留后、broker 接收后、领取后、外部 I/O 已成功但回包前、结果保存后、业务 commit 后、Report 后、ACK 前、GC 授权后及清理先完成而旧调用仍在途。

现有 `Committer.AfterCommit` 可复用。其他需要的故障点、可控对象存储代理、进程控制器和网络代理属于**待补测试设施**；不得描述为已有。仅测试进程/测试构建启用，不提供未鉴权的生产故障 HTTP 开关。

### 9.2 最低矩阵

| ID | 故障对象 | 注入方式/组合 | 必查行为 |
|---|---|---|---|
| FI-01 | 任一计算 worker | SIGTERM、SIGKILL、SIGSTOP 超过 lease，再恢复 | 优雅停止/失租两条路径均正确；旧外部调用无害；最后一次执行能收敛 |
| FI-02 | async-control | Relay 与 scheduler 分别暂停；进程强杀；备用接管 | 模块独立，位点/预算持久；已运行任务不因调度器停机立即丧失续租 |
| FI-03 | committer | 事务前/中/后强杀，保留未 ACK 结果 | 效果/receipt 原子，接管后补回报；每个分片正常推进 |
| FI-04 | 控制 PG | 断连/黑洞/慢响应/连接耗尽/只读/重启 | API 事实事务仍可按契约提交；后台退避、不 ACK 未持久结果、不丢预算 |
| FI-05 | 业务 PG | 读连接失效、写连接失效、锁等待、磁盘/连接压力、进程重启 | 不报假成功；事实/receipt 原子；可恢复错误与永久冲突区分 |
| FI-06 | RabbitMQ | 连接/confirm 黑洞、consumer cancel、资源告警、重启；集群分区另测 | 有界窗口/退避；持久工作/结果可恢复；dead 出口有归属 |
| FI-07 | MinIO | 延迟、部分传输、RST、成功丢响应、禁止读/写/删、重启 | 阶段判定正确、有限重试；旧/共享字节安全；输出位置可追踪 |
| FI-08 | Redis | 不可用、慢/半开连接、恢复期间缓存旧值 | 预算内回退，事实权限正确；不影响控制库执行权威 |
| FI-09 | 网络不对称 | A 可写业务库但不能续控制租约；A 可到 MinIO 不能到控制库；MQ 正常但 PG 黑洞 | 无本地标志代替 fencing；结果/副作用在失租后安全处理 |
| FI-10 | 时间 | 进程 clock 偏移 ±5min；DB 时间边界；单调计时/墙钟差异 | lease/到期以数据库时间为准；不提前清理；不修改宿主机全局时间 |
| FI-11 | 资源 | worker CPU 限额/OOM、磁盘接近配额、文件描述符/连接上限 | 有界内存/线程/连接；失败有持久归属；测试宿主机保留恢复余量 |
| FI-12 | 复合故障 | worker 结果已保存 + committer 停止 + control 重启；MinIO 未知成功 + lease 接管 + 用户取消 | 中间态可恢复；不因多次恢复刷新预算/误删新输出 |
| FI-13 | 恢复风暴 | 中断积累后同时恢复 MQ/worker/committer，大量通知重投 | 全局在途/写预算仍有效；必要收尾优先；API 不被瞬时洪峰拖死 |

故障场景至少覆盖：小于 lease、超过 lease、超过一次执行 timeout、直到某项有限预算耗尽。真实 lease 接管保留秒级等待；较长 timeout/截止时间和预算耗尽使用可控时钟或专用夹具调整持久时间/预算来验证，默认参数另做配置关系校验，不等待小时/日级自然期限。不能为加速而关闭 token、删除授权或跳过业务前提。

### 9.3 恢复时限的判定

不使用“等到成功”为无限等待。执行前记录 `poll_max`、lease、consumer 重连上限、重试 cap、任务/提交 deadline。

- 无积压、依赖恢复后的模块/分片接管目标：不超过 `2 × lease + 2 × poll_max + 重连上限`。重连上限从实现/实际配置核实；缺少有界机制时先暴露为缺口，不随意填常数。
- computed 补发目标：不超过下一次持久 `not_before` + 2 个轮询周期 + 可用提交排队预算；计算次数必须不变。
- 短样本全链路默认目标：单步 60s、全程 5min；实际样本大于 10MiB 或故意慢 I/O 的场景单独配置，不能拿它认证生产 SLA。
- 预算耗尽收敛：最后有效租约/执行结束后，在有限恢复扫描与协调期限内进入明确停止/人工状态；不能强行要求所有资源均已自动清理。
- 时限内未收敛即 FAIL；依赖始终未恢复导致无法观察恢复时是 BLOCKED，同时保留已检测到的安全性失败。

| DR-04 | P0/E2/E3 | 控制备份落后且 outbox 已超过保留窗口，停止屏障也不在备份 | 明确不可自动证明；停写/隔离/人工恢复，不宣称“事件总能重建” |
| DR-05 | P1/E3 | 应用主机丢失/网络分区/恢复；有 HA PG 时主切换/旧主隔离 | 原始配置下 RTO/RPO 实测；单写主正确；没有基础设施环境则 BLOCKED |
| DR-06 | P1/E3 | 三节点 MQ 成员故障/多数派恢复；集群 MinIO 节点故障 | 各自持久性/恢复语义与应用去重共同成立；结果按基础设施拓扑单列 |

DR-01 的特别门槛：业务 receipt 能阻止已经生效的业务重复执行，但不能独自恢复尚未生效任务已耗尽的执行预算。必须验证实际备份/PITR、保留的控制 WAL 或其他持久屏障能够保住对应结论；若无法证明，应报告恢复点的数据损失/人工处置范围，不能让测试自动重新给满预算后算通过。

恢复演练先保存故障点与数据清单，所有操作在恢复副本中执行。每轮报告备份时间、恢复点、WAL/事件覆盖、MQ 残留处理、对象存储版本能力、RPO/RTO 和不可自动恢复集合。

## 11. 短时压力、背压与资源边界

正确性通过后再提高负载；每档都运行 INV 判定器。短时压力验证资源上限、锁竞争、公平、背压和恢复风暴。单个负载场景默认 5min、硬上限 10min，整个短时压力执行包（含变体与排空）硬上限 60min；达到上限立即结束发压并在预留恢复时间内对账，不通过自动延长时长寻找绿色结果。

本执行包不认证长期稳定性、长期泄漏或可持续生产容量；不安排小时级稳态发压或浸泡任务。

### 11.1 工作负载

| ID | 工作负载 | 设计 |
|---|---|---|
| LD-01 | 均匀业务混合 | create/complete、秒传、分享导入、删除/GC、缩略图；按实际用户比例记录，初始建议 50/15/10/15/10 |
| LD-02 | 热点 owner | 80% 流量来自 1 owner，其余 20% 来自 31 owner；记录 owner 额度、公平进展与 API 延迟 |
| LD-03 | 共享对象争用 | 多 owner 同内容上传/秒传/分享导入与最后引用删除；持续读 SHA/引用/配额 |
| LD-04 | 写慢与恢复 | 主动降低 committer 配额/延迟业务写；积压跨 high，降载跨 low，再恢复峰值 |
| LD-05 | 小任务风暴 | 小文件/失败/取消/到期密集；覆盖消息吞吐、控制表热点、批合并、失败协调 |
| LD-06 | 大字节 I/O | 多分片大文件、图片解码、哈希；区分字节吞吐与任务速率，不拿小文件 QPS 外推 |
| LD-07 | 历史规模 | 固定活跃任务量，历史 0→10 万→100 万；测 Relay/到期/租约/维护/metrics 查询成本 |
| LD-08 | 辅助派生压力 | AI/search 饱和、外部后端慢/停，核心上传/必要 GC 仍进展；fake/真实 provider 分开 |

混合比例是建议输入，不是事实流量。记录产生任务的放大量，避免把一个上传衍生的多种任务当成多个用户操作吞吐。

### 11.2 短时阶梯、突发和恢复

1. 冻结硬件、连接/在途/写预算、分片和样本；记录空闲基线，只测当前系统，不重建旧系统性能项目。
2. 客户端并发候选为 1、2、4、8、16、32，每场景按资源预算选 2～3 档，每档预热 15s、采样 45～60s。达到资源保护线/错误/积压持续增长即停止升档。
3. 用独立到达率驱动短时复验，记录 offered/accepted/completed，避免闭环客户端慢下来掩盖服务延迟；测 P50/P95/P99、样本量和超时/拒绝，样本不足不外推分位数。
4. 在确定安全的专用环境施加一次 30～60s 突发或提交降速，观察背压/拒绝/积压；随后停止发压，预留不超过 2min 排空与恢复对账。未在时限内恢复则判 FAIL 并保留现场。
5. 按需要选择 1/2/4 实例短时对照，共用整个执行包的时间上限；验证全局额度没有翻倍，不逐组合重复长时间发压。
6. 每个结果只归属于当次硬件/配置/数据/依赖拓扑和观察窗口，不从短时或单机结果推导可持续生产容量。

写限速按 token bucket 判断：长度为 T 的采样窗口允许量不超过“实测速率预算 × T + 已配置桶初始/突发额度”；慢提交降速时采用当时有效预算。不能用单秒偶发突发就认定全局超额，也不能只看平均数掩盖采样期间的额度放大。

### 11.3 必采指标与建议门槛

| 维度 | 门槛/判定 |
|---|---|
| 正确性 | 全程 INV 违反为 0；任何文件字节损坏、越权、误删、重复结算立即停止该档并判 FAIL |
| 全局边界 | 有效 queue/owner 在途、worker 并发、write permit/事务、DB 池、消息 prefetch/confirm/batch 不超过配置语义上界 |
| 窗口内积压 | 报告每档未完成任务数、最老年龄和到达/完成速率；只判断观察窗口内趋势，不声称长期稳态 |
| 恢复 | 降载或故障恢复后在事先按积压量/实测提交速率估算的排空时限内收敛；不得无限延长观察窗口 |
| API 隔离 | 同等 API 负载下，异步受压 P95 相对健康对照初始目标不超过 1.5 倍，非预期 5xx <0.1%；属于待校准验收目标，测前冻结，不称现有 SLA |
| 公平/最低份额 | 持续合格 owner/低优先级类别均有进展，满足 SC-05/06 的算法预留上界；无永久饥饿 |
| 内存/协程/连接 | 检查采样期间是否超出配置上界，以及排空后 goroutine/连接能否回收；异常保留 pprof/趋势，短时观察不作长期泄漏结论 |
| 磁盘/WAL/历史 | 记录每业务操作带来的业务/控制行数、WAL、MQ/MinIO 增量；终态详情维护后有界，保留语义屏障的增长单列 |
| 延迟 | API、relay、排队、计算、computed→commit、补偿各段 P50/P95/P99；异步端到端用同一 trace，不相加不同样本的分位数 |

### 11.4 时间边界的快速验证

lease、timeout、任务/提交 deadline、延迟 GC 和 lifecycle 保留窗口继续通过配置断言、可控时钟、专用夹具时间戳和临界屏障验证。真实 lease 接管保留必要的秒级等待，小时/日级业务等待采用加速逻辑测试。加速验证的结论限定为边界逻辑，不声称默认自然时长已实测。

每个短时负载场景结束后停止生产、排空并检查终态、预算、receipt、引用、配额及已知输出；不增加耐久或浸泡续跑步骤。

## 12. 可观测性、诊断和测试设施交付

### 12.1 当前能用的观测与缺口

`asynccontrol/monitor.go` 当前暴露 live/ready、`bx_async_tasks`、按状态 updated_at 计算的 oldest age、执行/失租/派发/补发统计、commit calls/seconds sum/receipt hits、module active、Relay 位点/xmin 和最多 2000 行未接管样本、quarantine 数。

注意：

- `oldest_age` 基于 `updated_at`，不等于完整排队/端到端延迟；sum/calls 不能直接给 P99。
- Relay unaccepted 是有限采样，不等于全量积压；`seq` 单独也不等于安全位点。
- 当前聚合查询随历史量增长的成本，需要 LD-07/OP-05 验证。
- 分片所有权、write permits、队列深度、最老实际结果年龄、GC 扫描次数和细分延迟需用 SQL、MQ/PG 指标或新增测试观测采集；不能假定已有同名指标。

在每种故障下核实 live、ready、standby/owner 与积压的含义。API ready 不应因 MQ/控制库停机失败，但业务 PG 不可用必须按其真实 readiness 语义报告。故障预期错误与非预期错误分开，正常场景不允许未处理异常。

### 13.3 重复、race、fuzz 策略

| 类型 | 最低执行量（计划值） | 目的 |
|---|---|---|
| P0 确定性临界窗口 | 每个新窗口串行 20 次；缺陷修复后的最小复现 100 次 | 排除仅碰巧命中时序，重复不能替代屏障 |
| P0 真实进程 kill/接管 | 每个关键窗口 20 次，含原实例恢复 | 验证真实连接/ACK/事务结束行为 |
| 随机状态模型 | 固定回归 seeds + 至少 100 seeds × 1000 步 | 多步交错不变量；失败保留 seed/缩减序列 |
| fuzz | 每个新 target 5min、执行包累计上限 30min；只一个 target/进程运行 | 畸形输入/边界/状态组合；发现 corpus 入回归 |
| race | 核心与新增领域并发全包；新关键竞争用例再 `-count=10` | 数据竞态；不能用 race 通过代替分布式正确性 |
| 浏览器 E2E | Chromium 全路径至少 3 次独立 run；选定 Firefox/WebKit 关键路径 | 真实 UI/代理/浏览器兼容；不以自动重试隐藏 flaky |
| 故障组合 | 单故障矩阵先通过，再按固定 seed 做有界组合；单场景上限 10min | 验证多故障交错与恢复；不附加连续发压或浸泡 |

新增 fuzz target 的真实函数名、超时和 corpus 路径在实现后登记；本文不提供调用不存在函数的“可运行命令”。所有重复均有整体时间/资源上限，达到上限输出未完成集合，不能静默减少执行量后声称完整。

| 短时压力与资源边界 | LD、加速时间边界 IO-07 | 验证背压、限流、全局额度和恢复；长时间压测、浸泡及自然到期观察已取消，不作为阻塞项 |
| 跨主机/基础设施容灾 | E3、DR-05/06、MQ-09 集群部分 | 环境不具备就 BLOCKED，不能并入单机 HA 结论 |

“完整计划已执行”要求当前范围内所有计划用例都有结论与证据；“完整测试通过”要求全部所声明执行包满足门槛，未执行/阻塞包不能折算通过率。已取消的长时测试不计入用例分母，也不列为剩余待办。允许先出阶段报告供定位问题，但最终报告持续列出本轮范围内的剩余项。

### 14.3 缺陷与发布门槛

- S0：数据丢失、越权、有效对象误删/字节损坏、不可恢复的账目损坏。立即停止相关压力/故障链，保存现场，阻断验收。
- S1：事件/任务漏失、重复业务效果、预算无限刷新、终态复活、无限重试/补偿、关键恢复失败或资源无界。修复后最小复现、相邻窗口和完整相关包重跑。
- S2：可恢复但违反预定时限、某 owner 饥饿、错误展示/诊断不足、可控性能退化。明确影响范围与解决/处置，不静默忽略。
- 已接受的历史缺陷如 BE-07 保留独立编号和依据；不会因本计划自动变成新增修复授权，也不会变成 PASS。

正式验收：S0/S1 为零；所声明执行包 required case 无 BLOCKED/NOT_RUN/未知 skip；所有 P0 不变量和恢复窗口通过；S2/已知限制逐项可见；资源恢复、残留现场、未部署状态清晰；最终复跑与被测构建摘要一致。

不强行设一个全仓覆盖率百分比来代替正确性。需要附带改动核心的分支覆盖与未覆盖列表，关键状态/异常/ACK 窗口必须有场景证据，不能通过增加镜像式单测提高数字。

## 15. 报告模板与施工书追踪

### 15.1 每轮报告最少内容

1. 被测版本：HEAD + dirty 文件摘要、镜像/二进制、双库迁移、脱敏配置、依赖版本、环境拓扑。
2. 代码/测试设施变化与实际部署：分别写改了什么、测试环境启动了什么、用户业务环境是否变化。
3. 实际命令、开始/结束时间、退出码；测试顶层/子测试/包分别统计；旧 helper 和必需 skip 分开。
4. 按场景 ID 的 PASS/FAIL/BLOCKED/NOT_RUN/EXCLUDED/KNOWN_DEFECT、覆盖入口/任务类型/不变量。
5. 故障“实际生效”与恢复时间线、原始状态/预算/ACK/字节证据；不只写故障脚本退出 0。
6. 配额/引用/receipt/来源/位点/结果/输出清理对账，短时负载、资源边界、恢复结果及观察窗口。
7. 首次失败、复现、根因、修复、回归与仍未解释的 flaky；不覆盖首次失败记录。
8. 尚未运行/受阻的辅助包、跨主机/集群、备份窗口、加速时间边界结论和已知缺陷；长时压测/浸泡/自然到期观察只在范围说明标注已取消，不列作待办。
9. 测试资源、故障恢复、保留现场、建议清理清单、证据归档位置；不自行删除用户资源。
